# HRU507 / S-L5-008 — Chronos-2 Zero-Shot Multivariate Forecasting

**University research prototype — localhost only.** A reproducible experiment for temperature (°C), relative humidity (%RH), and CO₂ (ppm), forecasting **5, 10, and 15 minutes ahead** from 1-minute sensor data. Developed to compare with a different team member's **custom-trained PyTorch Transformer**. The source model is used **as pretrained**. There is **no training, fine-tuning, cloud deployment, chatbot, or RAG**.

> **Scientific integrity:** The supplied CSV declares `HYBRID_OBSERVED_PROXY_AND_SIMULATED` for the dataset. Temperature is a source `ZONE_TEMP_1` proxy with **assumed Fahrenheit units**; RH and CO₂ were generated by **synthetic physical mass-balance models**. Those targets are suitable for a *prototype or simulation-based forecasting comparison* but **cannot validate predictive accuracy on physical building sensors**. The experiment preserves and records provenance. Independent verification of the original temperature units is necessary.

## 1. What is Chronos-2? (EN / 中文)

Chronos-2 is a **pretrained time-series foundation model**. Amazon researchers describe it as an *encoder-only* model using grouped attention to share information between related time series (like temperature, RH and CO₂). It produces quantile forecasts, including a **median point forecast**, without fitting its parameters to our local AHU dataset. Its pretrained knowledge may or may not generalize well to this hybrid sensor dataset; the experiment measures this rather than assumes it.

- **Zero-shot / 零样本预测:** load already-learned weights, pass the previous 60 or 180 readings, and forecast the next 15. **Do not run `.fit()`**.
- **Multivariate / 多变量:** the three histories are sent in *one jointly grouped window* of shape `[batch, 3, context_minutes]`. Chronos-2 can model relationships among channels, though such sharing is not guaranteed to improve results.
- **No future leakage / 避免资料泄漏:** to predict from timestamp `t`, the model sees **only `t-context+1` through `t`**. Future values `t+1..t+15` are used **only as evaluation labels**.
- **Quantile forecast / 分位数预测:** `p10`, `p50`, `p90` form an 80% central prediction interval; **`p50` is the point forecast**. The model's API labels it a 'mean', but source code explicitly returns the median.

Primary sources: [Amazon's official Chronos repository](https://github.com/amazon-science/chronos-forecasting); [official Chronos-2 pipeline/API](https://github.com/amazon-science/chronos-forecasting/blob/main/src/chronos/chronos2/pipeline.py); [Ansari et al., *Chronos-2: From Univariate to Universal Forecasting*, 2025](https://arxiv.org/abs/2510.15821). See `RESEARCH_NOTES.md` for citations and the method comparison.

## 4. Quick start — recommended order

**Step A: Copy your CSV** to `data/HRU507_S-L5-008_1min_aligned.csv`.

**Step B: Verify inference isolation with a synthetic smoke test** (the fake values are **not research results**):

```bash
python main.py --self-test
```

**Step C: Run the true **persistence baseline** without downloading a model:**

```bash
python main.py --baseline-only
```

It generates `outputs/baseline_test_metrics.csv`, `outputs/baseline_test_forecast_paths.csv`, `outputs/baseline_test_example.png`, `outputs/baseline_events_metrics.csv`, and `outputs/dataset_audit.json`. These are **real-data baseline evaluations**, not Chronos-2 outputs.

**Step D: Run pretrained Chronos-2 inference and final test evaluation:**

```bash
python main.py --device auto
```

The default evaluates **60-minute and 180-minute** context candidates on a chronological validation segment; picks context using an equally weighted, train-standard-deviation-normalized MAE; and performs a single held-out test run. Context and validation are **not fine-tuning**. The default run uses **32** validation origins and **64** test origins spread evenly over their time periods; this is a **sampled evaluation**, not an exhaustive evaluation of all 525,540 rows. Make a stronger final report by increasing the counts when runtime allows:

```bash
python main.py --device auto --validation-origins 128 --test-origins 256 --batch-size 6
```

For a slower CPU: `python main.py --device cpu --validation-origins 12 --test-origins 24 --batch-size 1` (an exploratory quick-check, not a robust final comparison).

**Step E: Open the notebook** to work through the method interactively; it imports tested functions from `main.py`. You can run the baseline first and then the pretrained run.

If the CSV is elsewhere, add `--csv "path/to/your.csv"`; if outputs should be elsewhere, add `--output my_results`.

## 5. Interpreting generated results

| Produced after Chronos run | Meaning |
|---|---|
| `validation_context_selection.csv` | Validation-only choice of 60 vs 180 minute context; **no test tuning** |
| `validation_context_60_metrics.csv`, `validation_context_180_metrics.csv` | Validation per variable / horizon |
| `chronos2_test_metrics.csv` | Held-out test MAE, RMSE, persistence scores, relative MAE skill, and p10–p90 coverage |
| `chronos2_test_forecast_paths.csv` | Actual/predicted values for every step from 1 to 15 minutes for sampled origins |
| `chronos2_test_example.png` | Actual vs Chronos p50 vs persistence, one test-origin example with uncertainty interval |
| `chronos2_events_metrics.csv` | Post-hoc exploratory scores at transitions selected by observed 15-minute changes |
| `chronos2_triggered_sensor_event_metrics.csv` | Sensor-specific event cases, not mixed event types |
| `experiment_metadata.json` | Model version ID, selected context, split methods, device, runtime (not full training time) |
| `dataset_audit.json` | Dataset provenance, SHA256, timestamps, 70/15/15 boundaries and simulation disclaimers |

**MAE / 平均绝对误差:** mean of `abs(predicted - actual)`. **RMSE / 均方根误差:** sqrt of mean squared error; emphasizes large mistakes. **Persistence / 持续性预测:** `prediction(t+h) = latest_observed(t)`; a transparent benchmark for slow-changing sensors.

**Skill vs baseline:** `1 - Chronos_MAE / Persistence_MAE`. Positive is better than persistence; negative is worse. For flat segments where baseline MAE is exactly zero, the skill field is left empty rather than dividing by zero.

**Event study:** An event threshold is the **98th percentile of absolute observed 15-minute changes** computed from the **training split only**. Test events are tagged from observed 15-minute outcomes for **diagnostic scoring only**. The future outcome is **never passed to the model**. Report event results separately: they are intentionally selected cases and are **not representative of all test minutes**.

**Fair Transformer comparison:** the other model must use the identical CSV/hash, split boundaries, forecast origin timestamps, horizon definitions, point-prediction rule, target variables, and metrics. A scratch-trained model should fit exclusively on **train**, tune on **validation**, evaluate only once on **test**. A pretrained model has no local training step. Use `COMPARISON_TEMPLATE.csv` for recording both numbers. State whether model inference was CPU/GPU, any execution differences, and that the signals were hybrid/simulated.

## 6. Known limitations

1. **Data provenance:** two of three targets are simulated, and temperature units were assumed from a source channel; no physical deployment claims.
2. **Generalization:** a model trained on diverse external datasets may experience **negative transfer** to this domain; compare objectively against persistence and the team Transformer.
3. **Evaluation sampling:** default origins are sparse/evenly spaced for affordable local inference. Increase origin counts for a defensible final report.
4. **Distribution shift:** one year of a single virtual asset and occupancy scenario is not independent multi-building evidence. Error statistics can vary by season, occupancy and transients.
5. **No certainty guarantee:** 10–90% predicted interval is a model interval; coverage on this dataset may be under or over 80%.
6. **No physical constraint enforcement:** predicted RH or CO₂ can hypothetically go outside physical bounds; the code **does not hide, clip, or silently correct those predictions**.
7. **Time and hardware:** single-device inference varies drastically; training the custom Transformer and loading Chronos-2 are different computational tasks, so report timings separately.
8. **Unsupported causal claim:** even multivariate forecasts cannot prove that CO₂ causes temperature changes or vice versa.

## 7. Sources and academic grounding

The official Chronos repository/API and Chronos-2 research paper above support the model architecture and inference usage. The user-supplied tutorial notebooks and worksheets motivate **cleaning and descriptive statistics**, **separate validation and test**, **continuous-value MAE/RMSE**, **overfit / underfit considerations**, **data-loader memory management**, and **pretrained-model evaluation without fine-tuning**. Their examples are mostly tabular regression and image classification, so those **general methodological principles** are adapted to **sequential** forecasting; we do *not* transplant shuffled splits, Colab Drive mounting, softmax classification loss or image augmentation into sensor forecasting.
